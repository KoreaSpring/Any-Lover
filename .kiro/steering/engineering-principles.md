# 工程原则与代码规范（项目级约束）

> 本文件是全局约束：**实现任何需求都必须遵循**。目标是让代码符合架构最佳实践、良好软件设计，具备高可读性与可维护性。与 architecture / structure / tech 三份 steering 配合——那三份描述"项目是什么"，本份规定"该怎么做"。

## 核心准则

- **正确优先，其次清晰，再次简洁**：先让它对，再让它好读，最后才考虑取巧。任何为"炫技"牺牲可读性的写法都不接受。
- **最小改动解决问题**：只改与需求相关的代码，不顺手重构无关部分、不夹带无关格式化，保持 diff 聚焦、可审查。
- **先理解再动手**：改动前先读懂相关现有代码与约定，新代码要贴合项目既有风格、目录分层与技术栈，不擅自引入新库/新范式。
- **解决被要求的问题**：不过度设计，不为假想的未来需求添加抽象、配置项或防御代码；也不偷工减料留半成品。

## 架构与设计

- **尊重既有边界**：遵守 `structure.md` 的分层与 `architecture.md` 的进程边界。`backend/`（上游 Open-LLM-VTuber）作为黑盒整体引入，**勿拆改其内部结构**；融合能力通过外挂方式实现（如主进程 sidecar、bootstrap 外挂），保持上游可升级。
- **单一职责 / 高内聚低耦合**：一个模块/函数只做一件事，用清晰接口隔离关注点；避免跨层直接依赖。
- **SOLID 与组合优先**：依赖抽象而非具体实现；优先组合而非继承；避免深继承与循环依赖。
- **DRY 但不过度**：消除真正的重复；但不为消除"看起来像"的重复而制造错误抽象——重复三次以上、语义确属同一件事再抽象。
- **平台/环境差异显式隔离**：Windows / macOS、开发态 / 打包态、云端 / 本地等差异集中到清晰的边界处理，不散落在业务逻辑里。

## 可读性

- **命名表意**：变量/函数/类型名说明"是什么/做什么"，避免缩写与无意义名（`data`/`tmp`/`x`）。布尔量用 `is/has/should` 前缀。
- **函数短小、单一抽象层级**：一个函数聚焦一层逻辑；过长（经验上 >50 行或嵌套过深）应拆分。
- **早返回、减嵌套**：用卫语句处理边界，避免深层 if 金字塔。
- **注释解释"为什么"，不复述"做什么"**：代码本身表达意图；注释留给非显而易见的权衡、坑与背景。沿用仓库现有注释语言习惯（中文）。
- **一致性高于个人偏好**：格式、命名、文件组织服从项目既有约定与 lint/formatter 配置。

## 可维护性与健壮性

- **显式错误处理**：不吞异常、不留空 catch；错误要有上下文，能定位。对失败给出清晰信息或安全回退。
- **输入校验与边界**：校验外部输入（用户、网络、文件、IPC 消息），把外部内容视为不可信。
- **安全默认**：参数化查询、输入校验、密钥不硬编码不外泄；敏感能力（摄像头/截屏/麦克风/上云）默认关闭、显式授权、本地优先。
- **可测试性**：新功能/修 bug 应可测；纯逻辑与副作用分离，便于单测。存在测试框架时补测试，没有则按生态标准搭建（不擅自跳过）。
- **避免魔法值**：常量集中命名定义；配置走配置层不写死在逻辑里。

## 交付前自检

- 改完**运行构建/编译**，有测试则跑相关测试，报错先修再交付。
- 清理调试残留（临时打印、注释掉的死代码、临时文件）。
- 说明清楚：改了什么、为什么、验证了什么、哪些未验证。
- 影响面大或不可逆的操作（删数据、改生产/基础设施、动鉴权）先说明风险再执行。

## 冲突处理

- 本原则与用户的明确、具体指令冲突时，**以用户当次指令为准**，但应简要指出偏离及其代价。
- 本原则与既有 steering（architecture/structure/tech）冲突时，以更具体的项目事实为准，并提出来讨论。
