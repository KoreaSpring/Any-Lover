# 升级路线：三项高风险工程的方案与决策点

> 本文是**方案与评估**，不含代码改动。三项都属中高风险、需要你在关键点拍板后才实施。
> 低风险改进（测试+CI、记忆时间感知、首句延迟保护、分发审计）已分别落地（见各自提交与 `docs/DIST_SECURITY_AUDIT.md`）。
> 对标依据见评估报告（会话内 artifact）与公开资料（Open-LLM-VTuber 发布说明、Mem0/LongMemEval、MCP 规范）。

---

## 一、同步上游 Open-LLM-VTuber

### 现状
- `backend/` 是某个较早的 vendored 快照 + any-lover 自己的扩展（见 `backend/ANYLOVER_EXTENSIONS.md`，9 个文件、git 基线 `f5bf9f6`）。
- 上游近一年已演进：**Letta 长期记忆、MCP 工具调用、Live2D Cubism 5、Bilibili 弹幕、异步重写、更模块化**。
- **意外发现**：上游的 **MCP 实现其实已经在我们的 vendored 快照里**了——`backend/src/open_llm_vtuber/mcpp/`（mcp_client / server_registry / tool_adapter / tool_executor / tool_manager / types）齐全，`backend/mcp_servers.json` 已配 time + ddg-search 两个 server。也就是说我们并不缺 MCP 代码，缺的是"中枢对话有没有用上它"（见第二节）。

### 成本 / 收益
- **收益**：拿到上游后续的 bug 修复、异步稳定性、Cubism 5、Letta 记忆等；减少自研重复。
- **成本/风险（高）**：上游有"配置破坏性变更 + 后端架构变更 + 前端完全重写"的历史（其 v1.0 就是 ground-up rewrite）。我们在 vendored 后端上有 9 处扩展，且**前端是我们自己基于早期上游深度改造的**（Electron 桌宠外壳，和上游的新前端已分道扬镳）。全量同步 ≈ 重新集成，极高风险。

### 建议：不做全量同步，做"挑拣式回合"
1. **先量化差距**：`git` 对比我们的 vendored 后端 vs 上游对应 commit，列出上游在 `mcpp/`、记忆、对话链上的具体增量。
2. **只回合后端能力、不碰前端**：我们的前端已是独立产品，不跟上游前端同步。
3. **按能力逐个回合**（每个独立验证）：优先 bug 修复与 MCP 完善；Letta 记忆视第二节决定（我们已自建时间感知记忆，不一定要换 Letta）。
4. **决策点**：是否值得投入？若后端对我们只是"ASR/TTS/表情服务 + 可选 MCP"，上游的对话/记忆演进对我们价值有限（因为我们在中枢自己做对话）。**倾向：只回合 MCP 相关 + 明确 bug 修复，其余不追。**

## 二、MCP 工具调用集成（让桌宠能"做事"）

### 现状
- 后端 MCP 代码已就位（`mcpp/`），`mcp_servers.json` 配了 time / ddg-search。
- 但**中枢对话（F-1/F-2）走的是我们自己的 `DialogueEngine`**（`agent/dialogue/dialogue-engine.ts`），它直接调 `LLMProvider.chat` 流式生成，**没有工具调用环节**——即中枢对话目前不会触发 MCP 工具。老后端对话链路可能用到 MCP，但那条链在中枢对话模式下被绕过。

### 目标
让中枢对话也能调用工具（查时间/搜索/未来扩展控桌面等），从"陪聊"升级到"能帮你做事的助手"。

### 方案（两条路，二选一）
- **路线 A（复用后端 MCP，推荐先验证）**：中枢对话需要工具时，把工具调用委托给后端已有的 `mcpp` 执行，结果回注中枢上下文再继续生成。改动在中枢 `DialogueEngine` + 一条到后端 MCP 的通道。复用成熟实现，风险较低。
- **路线 B（中枢自建 MCP 客户端）**：主进程(TS)直接起 MCP client 连 MCP server。更自主但要在 TS 侧重做一套 MCP 客户端，工作量大。

### 安全门控（**必须有，否则不能上**）
工具能读本地文件、搜网、未来可能控桌面——这是从"只说话"到"能动手"的质变，安全是前提：
- **默认关闭 + 显式授权**：工具调用默认关，用户在设置里逐工具开启（对标我们现有"摄像头/屏幕采样默认关"的门控范式）。
- **工具白名单 + 二次确认**：高风险工具（文件写、执行命令）调用前需用户确认。
- **沙箱/最小权限**：MCP server 以最小权限运行，不给桌宠无差别的系统控制权。
- **审计日志**：工具调用记入日志，可追溯。

### 分阶段
1. 阶段 1：只接**只读/低风险**工具（time、搜索），默认关，验证中枢对话 → 工具 → 回注 → 继续生成的闭环。
2. 阶段 2：加工具授权 UI + 白名单 + 二次确认门控。
3. 阶段 3：按需扩展更强工具（文件/桌面控制），每个都过门控。

### 决策点
- 路线 A 还是 B？（倾向 A，复用后端 mcpp）
- 第一批接哪些工具？（倾向 time + ddg-search，已配好）

## 三、对话链上移中枢（后端退为纯 ASR/TTS/表情服务）

### 现状
- 中枢对话（F-1/F-2）已能接管文字/语音对话，但**老后端对话链路仍在**，由"中枢对话开关"（`anylover_hub_dialogue`）切换。两套并存。
- 中枢侧 `DialogueEngine` 已做：上下文编排（人设+关系+画像+情绪+记忆）、流式逐句、历史、打断。

### 目标
长远让**所有对话编排在中枢**，后端只做 ASR/TTS/表情（能力 provider）。架构更清晰、单一事实源、便于加工具调用（第二节）与多模型路由。

### 对标
- Anima-LLM-Vtuber 的做法：把 ASR→LLM→TTS→emotion 编排成**单一 LangGraph 状态机**，provider 可换。我们不必引 LangGraph（主进程零依赖是优点），但可借鉴"单一状态机统管一轮对话生命周期"的思路。

### 风险（高）
- 动的是**核心对话链**，回归面最大：吞字/重复/口型不同步/打断失效/情绪表情错位等都可能回归。
- 老链路是用户当前的默认路径（中枢对话默认关），贸然切换影响所有用户。

### 分阶段（务必渐进，不要一次切）
1. 阶段 1：中枢对话模式**稳定性与功能对齐**老链路（多角色切换时中枢历史/人设同步、会话历史持久化——这几项在 ARCHITECTURE 待办里已列）。
2. 阶段 2：中枢对话从"默认关"变"默认开"，灰度验证，保留一键回退老链路。
3. 阶段 3：确认中枢链路全面不弱于老链路后，才考虑移除后端对话生成（后端只留 ASR/TTS/表情）。
4. 每阶段都要有：首句延迟、打断、口型/表情、多轮一致性的回归检查（部分可自动化，见已落地的测试基线）。

### 决策点
- 是否接受"分 3 阶段、每阶段单独验证、最后才拆老链路"的节奏？
- 阶段 1 的"中枢对话功能对齐"要不要现在启动？

---

## 优先级建议（综合三节）

1. **MCP 工具调用（路线 A，先接只读工具 + 门控）** —— 差异化价值最高，且后端代码已就位，起点好。
2. **对话链上移 阶段 1（功能对齐）** —— 为 MCP 和未来清晰度铺路，但只做对齐、不拆老链路。
3. **同步上游** —— 只挑 MCP 完善 + 明确 bug 修复回合，不全量追，不碰前端。
4. （并行）electron 大版本升级 —— 见 `docs/DIST_SECURITY_AUDIT.md`，安全收益大，独立任务。

> 以上每项实施前都需你确认具体范围与决策点。本文只提供方案，不代表已排期。
